# Ticket format and compatibility

Load when creating tickets, repairing structure or interpreting legacy syntax. Follow [the mandatory workflow](ticket-writing.md).

## Template

```markdown
# 05: Ticket title
Status: ready-for-agent
Execution: pending
Labels: backend, migration
Blocked by: 03, 04, authentication:02
Commits: none
Verbosity: 1

## Estado inicial

### Qué construir
A complete, observable result.

### Atomicidad
Why this result needs no interleaving after all dependencies complete.

### Criterios de aceptación
- [ ] Verify an observable outcome.

## Trabajo realizado
Pending.

## Estado posterior
Pending.
```

English headings `Initial state`, `What to build`, `Atomicity`, `Acceptance criteria`, `Work performed`, and `Final state` are supported. Conversations append under `Comentarios` or `Comments`. Preserve initial scope; record later decisions in the work log. Completion is explicit, not inferred from checkboxes.

For `Verbosity` selection and legacy defaults, follow the workflow's documentation levels. It is an authoring convention; the viewer has no selector.

Metadata is immediately after the first heading, before body sections. Readers also accept bold fields generated by `to-tickets`, execution aliases `open`, `claimed`, `resolved`, `done`, and dependencies separated by semicolons or commas. A bare number such as `03` always refers to the same feature. Use an exact feature-qualified reference such as `authentication:02` for another feature; never use partial feature names. Optional titles may follow references. `None (...)` and `Ninguno (...)` mean no dependencies. Consult `docs/agents/triage-labels.md` when present for custom triage strings.

Dependencies gate the whole ticket. Every ticket must be atomic: do not require stopping a ticket partway, implementing a dependency, then resuming it. Split that workflow into complete sequential tickets before implementation. Each ticket needs at least one implementation commit, recorded using its real abbreviated hash in `Commits:`.

Without `--strict`, original `to-tickets` and legacy records produce format warnings rather than forcing migration. Invalid identity, malformed values, duplicate fields, missing/ambiguous dependencies, self-dependencies and cycles remain errors. Unknown legacy status values remain readable with a warning. New tickets use the template and strict validation.

The validator is read-only: exit 1 means errors; exit 0 means no errors. It does not execute commands from tickets or prove atomicity, commit existence or claimed outcomes. The TOON discovery index contains metadata only: rows identify Markdown files; labels, blockers and commits are JSON-array strings in cells. Read the selected Markdown and its dependencies before implementation. Regenerate for current state; the index is never written to the repository.
