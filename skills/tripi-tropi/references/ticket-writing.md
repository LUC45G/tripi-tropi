# Writing atomic local tickets

These rules are mandatory when this guide is adopted by a repository's agent instructions. They apply to tickets created with `to-tickets` and to subsequent updates. The tripi-tropi viewer only reads files; the authoring or implementing agent maintains them.

## One complete result per ticket

- Store one ticket in `.scratch/<feature>/issues/NN-<slug>.md`, numbered from `01`, with a unique number within its feature.
- Define a complete, observable outcome and acceptance criteria that verify it. Keep the work small enough for a fresh agent context.
- Resolve every declared dependency before starting. Each dependency gates the entire ticket, never an intermediate step.
- Before publishing and again before implementation, review whether the ticket can finish without interleaving another ticket. If ticket 05 needs preparation, then 06, then more work on 05, replace that scope with three independently verifiable tickets: preparation, dependent work, and integration. No partial dependencies are permitted.
- Describe why the scope is atomic under `Atomicidad` or `Atomicity`. A validator can check structure and cycles, but cannot prove this semantic property; the agent must review it.

## Required metadata

Keep metadata immediately after the first heading, before the body sections. Use plain lines; readers also accept the bold field syntax generated by `to-tickets`. Preserve the author's language in titles and descriptions.

| Field | Meaning and values |
| --- | --- |
| `Status:` | Triage: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`. Use the repository's configured mapping if present. |
| `Execution:` | `pending`, `in-progress`, `blocked`, `completed`, or `discarded`. Legacy aliases `open`, `claimed`, `resolved`, and `done` remain readable. |
| `Labels:` | Comma-separated labels, or `none`. Triage roles are additionally exposed as labels by the viewer. |
| `Blocked by:` | Comma-separated ticket numbers in the same feature, or `none`. Readers accept semicolons, accompanying titles, `None (...)`, and `Ninguno (...)`. |
| `Commits:` | Comma-separated real abbreviated Git hashes (7–12 hex characters), or `none` before any implementation commit exists. Never invent hashes. |

Read `docs/agents/triage-labels.md` when a repository defines custom triage strings. Keep the execution state separate from triage in new tickets. A completed ticket must explicitly say `Execution: completed`; acceptance checkboxes indicate progress, not completion.

`Ready to implement` is calculated by the viewer, not written into `Execution:`: the ticket must be pending, approved as `ready-for-agent` or `ready-for-human`, have all dependencies completed, and have no critical structural errors. Triage or information requests stay pending. Only `ready-for-agent` tickets may be queued to Codex.

## Template

```markdown
# 05: Ticket title
Status: ready-for-agent
Execution: pending
Labels: backend, migration
Blocked by: 03, 04
Commits: none

## Estado inicial

### Qué construir
A complete, verifiable outcome from the user's perspective.

### Atomicidad
Why this ticket can finish without interleaving another ticket,
after every declared dependency is completed.

### Criterios de aceptación
- [ ] An observable outcome with a meaningful verification.

## Trabajo realizado
Pending. Record actual changes, decisions, and verification results here.

## Estado posterior
Pending. Record the result, problems, solutions, remaining work, and next step.
```

English headings `Initial state`, `What to build`, `Atomicity`, `Acceptance criteria`, `Work performed`, and `Final state` are also supported. Optional conversations append under `Comentarios` or `Comments`. Preserve the initial scope; record later decisions rather than silently rewriting its history. Acceptance checkboxes may be checked as work is verified.

## Implementation and commits

1. Read repository instructions, this guide, and the actual blockers. Revalidate their current state before implementing. Stop if the ticket is no longer ready or needs another ticket interleaved.
2. Record `Execution: in-progress` when work begins. Implement and verify one ticket at a time. Record observed changes and checks, including failures and unresolved limitations.
3. Make **at least one commit per ticket**, identifying its feature and number in the message, such as `feat(tripi-tropi #02): open local viewer`. Several commits for one ticket are allowed; mixing different tickets in one commit is prohibited. Keep unrelated work out of the commit. Push only when explicitly requested.
4. Obtain the actual implementation hash with `git rev-parse --short=12 HEAD`, then append it to `Commits:`. Record all implementation commits, preserving existing entries. The viewer displays these abbreviated hashes in the table/detail without changing them.
5. Save the hash and final ticket record in a subsequent commit for that same ticket, such as `docs(tripi-tropi #02): record implementation and result`. This bookkeeping commit does not need its own hash in `Commits:`: requiring it would create an endless self-reference. Implementation hashes are the authoritative trace; bookkeeping commits remain discoverable through Git history.
6. Set `Execution: completed` only after acceptance criteria are verified, the result is recorded, and an implementation commit exists. If Git or required checks are blocked, retain an unfinished execution state and document the limitation; never invent a hash or claim closure.

## Validation and existing tickets

Run `node <skill-directory>/scripts/validate-tickets.mjs --repo <repo> --strict` for tickets adopting this guide. Add `--feature <slug>` to limit validation to that feature. Exit code 1 indicates errors; 0 indicates no errors. The validator never writes files or executes commands from their content.

Without `--strict`, original `to-tickets` and legacy records are read with format warnings instead of requiring migration. Invalid identity, malformed values, duplicate fields, missing/ambiguous dependencies, self-dependencies, and cycles remain errors. Unknown legacy status values are retained with a warning. Structural validation is necessary; atomicity and the truth of claimed results also require agent review.
